Тема ДП(Р): Разработка веб-информационной системы агрегации и анализа вакансий из нескольких источников с поиском, фильтрацией и уведомлениями на почту.
Утверждена (распоряжением) от «06» апреля 2026 года № 18.01-17-156
Дата выдачи задания: «06» апреля 2026 г.
Исходные данные к работе (цель, задачи и объем исследования, предполагаемые методы и методики исследования и т.д.)
Цель: Разработать и внедрить программный комплекс (вебприложение) для централизованного поиска и просмотра вакансий, автоматического пополнения каталога из открытых источников (API HeadHunter и открытые данные портала «Работа России»), разграничения данных по источнику, а также для организации взаимодействия пользователей (соискатели, работодатели, модераторы и администраторы) в рамках единой платформы, с целью сократить время подбора вакансий и повысить актуальность отображаемых предложений о работе.
Технологии:
Язык программирования: Python (версия согласно среде разработки, не ниже 3.10, на практике используется 3.14).
Вебфреймворк: Django 4.2.29.
API: Django REST Framework 3.16.1.
Документация API: drf-yasg 1.21.15, drf-spectacular 0.29.0.
Асинхронные фоновые задачи: Celery 5.6.2, брокер/кэш: Redis 7.2.1 (через библиотеку redis).
HTTPклиент и разбор HTML: requests 2.32.5, beautifulsoup4 4.14.3, lxml 6.0.2.
Работа с изображениями: Pillow 12.1.0.
Документы резюме: python-docx 1.2.0.
Уведомления: python-telegram-bot 22.6.
Конфигурация окружения: python-dotenv 1.2.2.
Платформа разработки и эксплуатации (локально): ОС Windows 11; клиентская часть – веббраузер (Яндекс браузер).
Инструменты:
Среда разработки: Visual Studio Code.
Система контроля версий: Git.
Виртуальное окружение: venv (входит в стандартную поставку Python).
Менеджер зависимостей: pip (совместимый с используемой версией Python).
Запуск и отладка: Django development server (manage.py runserver), при необходимости – скрипт совместного запуска компонентов (run_all.py).
Очередь задач: Celery worker, планировщик Celery Beat.
Контейнер брокера сообщений и кэша: Redis (сервер версии, совместимой с клиентом redis 7.2.1).
СУБД: SQLite (встроенная в Python; файл базы данных проекта).
Тестирование: pytest 9.0.2, pytest-django 4.12.0.
Нагрузочное тестирование (при использовании в работе): Locust (версия – по requirements.txt/locustfile.py в проекте, при отсутствии фиксации – указать фактическую).
Документация REST: встроенные Swagger UI и ReDoc (через drf-yasg).
Входные данные:
Данные внешних API: JSONответы HeadHunter (api.hh.ru) при выгрузке вакансий, справочников, описаний, данных работодателя; JSON/XMLструктуры открытых данных «Работа России» (opendata.trudvsem.ru) при импорте вакансий.
Учётные и профильные данные пользователей: логин, пароль, ФИО, контакты, сведения профиля соискателя (образование, опыт, навыки, ожидания по зарплате, город, метро и др.), сведения профиля менеджера (компания, контакты, логотип).
Файлы пользователей: изображения аватара, логотипа компании, загруженный файл резюме (Word), иные документы профиля (если предусмотрено моделью).
Данные форм: параметры фильтров на списке вакансий (регион, зарплата, формат работы, источник вакансии, расписание, тип занятости и др. по реализованным полям); данные создания и редактирования вакансии на сайте; данные жалоб и модерации; события календаря и собеседований; сообщения чатов.
Конфигурация среды: переменные окружения и файл .env (ключи API, интервалы синхронизации, параметры пользовательского агента для HH и др.).
Служебные данные: расписание периодических задач Celery Beat; кэш и блокировки в Redis; входящие обновления Telegram Bot API при обработке команд ботом (если бот включён в состав комплекса).
Требования:
Обеспечить публичный просмотр каталога вакансий с пагинацией и многосоставными фильтрами (в том числе отдельный выбор источника: только HeadHunter, только «Работа России», все внешние, только размещённые на сайте).
Обеспечить карточку вакансии с явным указанием источника, корректным переходом на внешнюю площадку для отклика, для вакансий HH – подгрузка подробного описания и отображение рейтинга работодателя (по реализованной логике); для «Работа России» – отображение структурированного описания и адреса для карт в соответствии с данными источника.
Реализовать фоновый импорт вакансий с заданной периодичностью: отдельные задачи для HeadHunter и «Работа России», с инкрементальным отбором новых записей по курсорам (время публикации или изменения) и ограничениями объёма за один запуск согласно настройкам.
Обеспечить устранение устаревших записей: для вакансий HeadHunter – проверка доступности через API и деактивация недоступных; для «Работа России» – проверка статуса и удаление из локальной базы вакансий, отсутствующих в источнике (по реализованным задачам).
Предусмотреть защиту от конкурентной записи в SQLite при параллельном импорте (например, глобальная блокировка очереди загрузки с повтором задачи при занятости).
Реализовать ролевую модель: соискатель, менеджер (работодатель), модератор, администратор – с разным набором доступных действий (размещение вакансий, отклики, чаты, жалобы, панель модерации и администрирования – по факту реализованных разделов).
Обеспечить REST API с сессионной авторизацией и документацией Swagger/ReDoc с ограничением доступа к документации для администраторов (как в проекте).
Реализовать уведомления по расписанию (например, напоминания о собеседованиях и заметках календаря) через фоновые задачи.
Обеспечить корректную работу в среде Windows: вывод служебных сообщений без ошибок кодировки при кириллице в консоли (обработка в командах импорта и агрегаторе логов).
Предусмотреть резервное копирование базы данных по расписанию (задача Celery), экспорт/восстановление – в объёме, реализованном в проекте.
Выполнить требования методических материалов к оформлению пояснительной записки, тестированию (функциональные и нефункциональные виды по ISO/IEC 25010) и приложениям (текст программы, руководство пользователя, сценарии испытаний).

1.2. Обозначение испытуемой программы
Под испытуемой программой понимается программный продукт – веб-приложение JobFlex, реализованное средствами Python, фреймворком Django и связанным программным окружением согласно пояснительной записке и техническому заданию. Приложение функционирует как клиент-серверная система с обращением из браузера пользователя к серверу приложения и использованием SQLite в качестве локального хранилища данных (файл базы данных приложения).
Обозначение объекта испытаний заключается в необходимости подтверждения работоспособности, корректности реализации основных функций, достаточной устойчивости при допустимых искажениях входных данных и недоступности внешних сервисов (в объёме, указанном в документе), а также соответствия результатов работы приложения описанию, приведённому в пояснительной записке и настоящем приложении. Испытания выполняются в условиях эксплуатации по месту проведения тестирования и не заменяют промышленную сертификацию программного обеспечения.
1.3. Область применения объекта
Область применения объекта – автоматизация процессов подбора персонала и сопровождения вакансий на платформе JobFlex. Системой пользуются четыре категории пользователей. Соискатели применяют платформу для поиска вакансий по расширенным фильтрам, отправки откликов, переписки с работодателями, планирования собеседований и отслеживания статусов этапов найма. Работодатели размещают вакансии без ограничения по числу записей на период их актуальности, управляют откликами, назначают собеседования и просматривают аналитику подбора. Модераторы обеспечивают контентный контроль: рассмотрение обращений и состояний модерации вакансий, действия по скрытию или восстановлению публикаций в соответствии с правилами платформы, просмотр служебной аналитики в рамках своей роли. Администраторы обеспечивают работоспособность и администрирование платформы: управление учётными записями пользователей, просмотр журнала действий, резервное копирование и восстановление файла базы данных SQLite, а также иные сервисные функции панели администратора.
2. ЦЕЛЬ ИСПЫТАНИЙ
Целью проведения испытаний является проверка стабильной работы web-приложения JobFlex на персональном компьютере, включая корректность функций регистрации и авторизации пользователей, управления вакансиями и откликами, назначения собеседований, работы чата и уведомлений, а также функций администрирования платформы.

3.2 Требования, подлежащие проверке
В каталоге вакансий важно подтвердить, что данные отображаются корректно при любом наборе входных условий: страница каталога отрабатывает пагинацию, сортировку и фильтры (по региону, зарплате, формату работы, опыту, графику и ключевым навыкам), а переходы между каталогом и карточкой вакансии работают стабильно. В карточке должны выводиться все ключевые поля, рейтинг работодателя из HH.ru и DreamJob, карта 2ГИС и статус отклика пользователя. Любые изменения – создание вакансии, редактирование и архивирование – сохраняются в базе данных и сразу отражаются в интерфейсе без артефактов и конфликтов. Экспорт откликов в CSV должен возвращать корректный MIME-тип, кодировку UTF-8 и полный состав колонок.
Разграничение доступа – отдельный акцент. Тесты подтверждают, что авторизация через сессии Django обрабатывается правильно, а права ролей применяются последовательно: соискатель не может откликнуться на собственную вакансию, подать два отклика на одну позицию или получить доступ к панели администратора. Работодатель не видит чужих вакансий в режиме редактирования. Администратор имеет полный набор действий. Ошибки доступа возвращаются кодами 401 и 403 с понятными сообщениями, без утечки внутренних деталей и трассировок стека.
Безопасность уровня запросов проверяется на корректность валидации входных данных: параметры фильтрации не пробрасываются в сыром виде в базу, некорректные значения возвращают контролируемые ошибки 400 с описанием, а ответы при граничных значениях, пустых строках и конфликтующих параметрах остаются предсказуемыми.
Бизнес-операции – отклик на вакансию, назначение собеседования и изменение его статуса – тестируются как транзакционные сценарии. Здесь важно показать согласованность: при изменении статуса отклика на «приглашение» автоматически создаётся запись о собеседовании, уведомление отправляется через Telegram и email, а состояние связанных сущностей (отклик, собеседование, уведомление) остаётся консистентным. Тесты покрывают повторные отклики, отмену и перенос собеседований, корректность напоминаний за 24 часа и за 1 час до начала.
Для аудита требуется зафиксировать, что факты создания, обновления и удаления сущностей корректно записываются в журнал ApiActionLog и доступны для проверки. Поля before_data, after_data, роль исполнителя, HTTP-метод и время действия должны попадать в журнал последовательно, а чтение записей не влияет на бизнес-логику.
Фронтенд-поведение проверяется на устойчивость навигации и актуальность данных после операций. Переходы между каталогом, профилем, чатом и календарём, а также повторное открытие карточек не должны приводить к рассинхронизации: интерфейс обязан обновлять данные после ответа сервера. Сообщения об ошибках API конвертируются в понятные пользователю уведомления и не дублируются после успешных повторных действий.
Нефункциональные аспекты включают корректную обработку таймаутов при недоступности внешних API (HH.ru, DreamJob, 2ГИС, Telegram), устойчивость к сетевым сбоям и корректное логирование фоновых задач Celery. Логи сервера не должны содержать чувствительные персональные данные, а уровни логирования настроены так, чтобы в рабочем режиме сохранялась достаточная наблюдаемость для расследований без утечки отладочных деталей.

3.4. Модули
В рамках функционального тестирования проверялись следующие логические модули веб-платформы JobFlex.
Каталог и фильтрация вакансий – выдача списка активных вакансий, пагинация, сортировка, расширенные фильтры (в том числе по региону, зарплате, формату и графику работы, опыту, навыкам и др.), сохранение и применение пресетов фильтров при наличии данной функции в интерфейсе.
Карточка вакансии и отклики – отображение полей описания, ключевых навыков, условий и контактных данных, статуса вакансии, интеграционных блоков (рейтинг работодателя, карта и маршрут при подключении внешних сервисов); оформление и ограничение отклика (включая защиту от повторных и недопустимых сценариев), закладки.
Личный кабинет соискателя – профиль и документы (в т.ч. резюме и аватар при реализации), образование и опыт работы, настройки уведомлений и привязки мессенджеров, списки откликов и избранного, аналитика активности при наличии в системе.
Личный кабинет работодателя – управление своими вакансиями (создание, редактирование, архивирование и восстановление), просмотр и обработка откликов, экспорт данных при наличии, логотип и реквизиты компании, аналитика по вакансиям.
Модерация (роль модератора) – сценарии рассмотрения материалов, связанных с вакансиями (жалобы, состояния модерации, скрытие/возврат публикаций и др. – в объёме, реализованном в платформе).
Коммуникации – список диалогов, переписка, вложения, отметки прочтения, ограничения по размеру и типам файлов.
Календарь и собеседования – пользовательские заметки и отображение запланированных собеседований; назначение, перенос и отмена собеседований соискателем и работодателем при реализации на стороне работодателя/системы.
Уведомления – доставка служебных и напоминающих сообщений каналами, предусмотренными конфигурацией (например, Telegram-бот и электронная почта с учётом согласий пользователя), включая напоминания о собеседованиях при наличии фоновой обработки.
Панель администратора – обезличенная здесь совокупность функций управления платформой: пользователи, журнал действий API, операции резервного копирования и восстановления базы данных, просмотр справочной документации API при наличии.
Интеграции с внешними сервисами – загрузка и обновление данных вакансий и работодателей из внешних источников (в частности HH.ru и иные источники, реализованные в проекте), использование сторонних API для карты и маршрутов (например, 2ГИС) при их подключении; устойчивое поведение при недоступности внешнего API.
Фоновые задачи (Celery) – периодические и отложенные операции: напоминания, синхронизация и догрузка данных, резервное копирование по расписанию – в соответствии с реализацией в проекте.
Перечень модулей согласован с составом подсистем, описанным в пояснительной записке и реализованным в исходном коде веб-приложения JobFlex.
3.5. Контроль целостности данных
При проведении испытаний подлежит подтверждению согласованность данных в базе SQLite при выполнении типовых операций: создание, изменение и логическое завершение жизненного цикла записей (в том числе вакансий, откликов, сообщений чата, собеседований, пользовательских справочников и записей журнала действий). Требуется отсутствие рассогласований между связанными сущностями после транзакционных сценариев (например: отклик – изменение статуса – создание записи о собеседовании – фиксация событий в журнале ApiActionLog при реализации в системе).
Проверке подлежит соблюдение правил целостности на уровне модели данных (уникальные ограничения, внешние ключи, каскадное поведение там, где оно предусмотрено реализацией) и корректность отражения результата в пользовательском интерфейсе после обновления страницы без «залипания» устаревших значений после успешного ответа сервера.
Развёрнутое описание схемы данных, ограничений и технологии хранения приведено в пояснительной записке (соответствующие разделы структуры данных, технологической части и приложений к документации). В приложении Г фиксируются методические требования: при прохождениях сквозных сценариев исполнитель должен при необходимости сопоставлять состояние связанных таблиц до и после операции, а также подтверждать сохранность целостности при операциях резервного копирования и восстановления файла базы данных SQLite.

1.2 Область применения программы
Web-приложение JobFlex предназначено для автоматизации процесса подбора персонала и используется соискателями, работодателями и администраторами через браузер и REST API. Интеграции с внешними сервисами HH.ru, DreamJob, 2ГИС и Telegram Bot API расширяют возможности платформы. Область применения – компании, кадровые агентства и частные работодатели, которым необходима единая web-платформа для размещения вакансий, взаимодействия с кандидатами и контроля процесса найма.

Функциональным назначением программы JobFlex является обеспечение полного цикла взаимодействия между соискателями и работодателями в процессе подбора персонала: ведение каталога вакансий с расширенной фильтрацией по региону, зарплате, формату работы, опыту и ключевым навыкам, просмотр карточек вакансий с рейтингом работодателя и картой маршрута, отправка откликов с сопроводительным письмом и отслеживание их статусов, планирование и сопровождение собеседований с автоматическими уведомлениями через Telegram и email, ведение переписки через встроенный чат, управление личным профилем и резюме соискателя, а также предоставление аналитики и инструментов администрирования платформы.

Платформа обеспечивает безопасную обработку персональных данных в соответствии с ФЗ-152 и стабильную работу для трёх категорий пользователей: соискателей, работодателей и администраторов.

Для описания процесса использована методология IDEF0 (ICOM: входы – слева, управление – сверху, выходы – справа, механизмы – снизу). Выбран подход «контекстная диаграмма верхнего уровня (A0) – декомпозиция по уровням детализации».

В настоящем программном документе приведены диаграммы классов web-приложения JobFlex.
Документ содержит описание доменной модели (сущности и связи предметной области) и модели прикладного API-слоя (представления, функции, декораторы и вспомогательные элементы), используемых при реализации системы агрегации и анализа вакансий.
В документе представлен раздел «Диаграмма классов» со следующими подразделами:
Диаграмма классов предметной области
Диаграмма классов API-слоя
Назначение диаграмм классов в архитектуре проекта
В подразделе «Диаграмма классов предметной области» приведён состав основных сущностей системы JobFlex, их атрибуты и связи.
В подразделе «Диаграмма классов API-слоя» приведены элементы прикладного уровня, реализующие доступ к функциям системы, ролевую авторизацию и обработку пользовательских сценариев.
В подразделе «Назначение диаграмм классов в архитектуре проекта» сформулирована роль диаграмм для сопровождения, тестирования и развития программного продукта.

На рисунке 1 приведена диаграмма классов предметной области web-приложения JobFlex.
Рисунок 1 – Диаграмма классов предметной области web-приложения JobFlex
В таблице 1 представлены классы и краткое описание каждого класса предметной области.
Таблица 1 – Описание диаграммы классов предметной области web-приложения JobFlex
№
Наименование
Описание
1
2
3
1
User
Пользователь системы (встроенная модель Django). Хранит логин, email, пароль, имя, фамилию и служебные признаки учётной записи.
2
Applicant
Профиль соискателя. Расширяет User данными о местоположении, гражданстве, навыках, ожидаемой зарплате, Telegram, согласиях на уведомления и резюме.
3
Education
Запись об образовании соискателя. Связана с Applicant; хранит уровень, учебное заведение, факультет, специализацию, год окончания.
4
ExtraEducation
Запись о дополнительном образовании (курсы, сертификаты). Связана с Applicant.
5
WorkExperience
Запись об опыте работы. Связана с Applicant; хранит компанию, должность, период и обязанности.
6
Manager
Профиль работодателя. Расширяет User данными о компании, логотипе, телефоне и Telegram.
7
Administrator
Профиль администратора системы. Используется для административных функций и контроля доступов.
8
Moderator
Профиль модератора. Отвечает за обработку жалоб и модерацию контента вакансий.
9
Vacancy
Вакансия. Хранит название, компанию, регион, зарплатные параметры, формат работы, описание, требования, условия, статус активности и координаты.
10
Employer
Внешний работодатель (источники вакансий). Хранит идентификатор источника, логотип, рейтинги и служебные данные синхронизации.
11
Application
Отклик соискателя на вакансию. Хранит статус и сопроводительное письмо; контролирует уникальность связки пользователь-вакансия.
12
Interview
Собеседование между работодателем и соискателем. Хранит дату, место, статус и флаги отправленных напоминаний.
13
Chat
Чат между работодателем и соискателем. Фиксирует участников и состояние видимости/удаления по сторонам.
14
Message
Сообщение в чате. Хранит текст, файл-вложение, время отправки и признак прочтения.
15
Bookmark
Закладка пользователя на вакансию.
16
VacancyView
Факт просмотра вакансии пользователем для аналитики.
17
FilterPreset
Сохранённый пользователем набор фильтров каталога вакансий.
18
UserUiPreference
Пользовательские настройки интерфейса (например, тема light/dark).
19
CalendarNote
Личная календарная заметка пользователя (дата, время, текст, цвет, статус напоминания).
20
ApiActionLog
Журнал действий API: роль, метод, путь, операция, код ответа, данные до/после.
21
HhArea
Справочник регионов внешнего источника вакансий.
22
HhDictionaryItem
Справочник словарных значений внешних источников (опыт, занятость, график и др.).
23
UserDocument
Пользовательский документ (тип, реквизиты, метаданные).
24
UserDocumentFile
Файловое вложение к пользовательскому документу.
25
UserFeedback
Обращение пользователя (предложение/критика) со статусом обработки.
26
VacancyReport
Жалоба на вакансию.
27
VacancyModerationState
Текущее состояние модерации вакансии.
28
ModeratorDeletionReport
Отчёт модератора по скрытию/удалению вакансии с обоснованием.
29
ModeratorDeletionPhoto
Иллюстративные вложения к отчёту модератора.
30
Review
Отзыв по вакансии/работодателю (в зависимости от реализации модуля).
